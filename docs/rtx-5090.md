# Qwen3.8 Flash on 4× RTX 5090 (consumer Blackwell, SM120)

Field notes from bringing `qwen3.8-flash` up on a workstation with four
GeForce RTX 5090 (32 GB) cards, Threadripper PRO host, stock Ubuntu. Upstream
exercises Qwen TP1/TP2 (DGX Spark, RTX PRO 6000); TP4 on 32 GB consumer cards
needed the changes in this fork. Everything below is measured on that box
(driver 610.57.04, CUDA 13.1 toolkit, torch 2.14.1+cu132).

## Host packages

Preparation and serving need three system packages that a stock image lacks
(each surfaced as an opaque failure without it):

```sh
apt-get install protobuf-compiler liburing-dev pkg-config
```

`protoc` builds the Helios package-schema bindings; `liburing` backs the b12x
checkpoint loader's io_uring bounce path; `pkg-config` is how it finds it.
Point JIT compilation at a ≥12.8 toolkit (`CUDA_HOME=/usr/local/cuda-13.1`):
the default `nvcc` 12.4 on this host only warned (`SM 120 requires CUDA >=
 12.8`) and kept going.

## Peer-to-peer: the real gate

Consumer Blackwell reports no CUDA peer access (`nvidia-smi topo -p2p` =
`GNS`, `can_device_access_peer` = 0). Flare's single-host TP collectives
(b12x PCIe one-shot family) map peer memory directly, so preparation dies at
collective bootstrap (`cuMemSetAccess: invalid device ordinal`). Three layers
had to line up before the data path — not just the capability — worked:

1. **GSP registry keys** (from [rtx-p2p](https://github.com/kacper-daftcode/rtx-p2p),
   a registry-key unlock for GeForce; tested on driver 590+, works on 610):
   ```text
   # /etc/modprobe.d/nvidia-p2p.conf
   options nvidia NVreg_RegistryDwords="RMDisableFeatureDisablement=1;EnableResizableBar=1;RMForceP2PType=1;ForceP2P=0x11;RMPcieP2PType=1"
   ```
   The first two keys alone load but leave `GNS` on this driver. The
   `RMForceP2PType`/`ForceP2P` pair turns the capability on (`topo -p2p` =
   OK) — and peer copies still returned zeros and peer kernels hung:
   capability is not a data path. **`RMPcieP2PType=1` (BAR1 mailbox P2P
   mode) is what makes peer transfers deliver data** on this platform,
   where the four GPUs sit in separate IOMMU groups / PCIe root complexes.
2. **IOMMU passthrough**: `amd_iommu=on iommu=pt` in `GRUB_CMDLINE_LINUX_DEFAULT`
   (+ `update-grub`, reboot). Installed before the mailbox key was found;
   whether mailbox mode still needs it is untested — it is the fleet-safe
   setting either way.
3. **Bake the drop-in into initramfs** (`update-initramfs -u`). Without it
   the module loads at boot from the initramfs copy of `modprobe.d` and the
   keys silently do not apply until a manual reload.

Verify the data path, not the capability bit (host-staged copies also
"work" and prove nothing): peer copies must return the source bytes, and a
small NCCL all-reduce must complete. With mailbox mode both pass; P2P
bandwidth in this mode still needs measuring (`rtx-p2p/scripts/p2p-bandwidth.py`)
before claiming the oneshot collective is competitive, not merely correct.

Note for NCCL users on the same host: enabling peer access changes the
transports NCCL selects. Re-baseline before comparing against numbers
recorded with P2P off.

## Export and serve (TP4, 8 concurrent requests, 3 MTP draft tokens)

```sh
.venv/bin/ignition export /path/to/Qwen3.8-Flash-Next-FP4-Local \
  --config /path/to/flare-config.toml \
  --gpus 0,1,2,3 --mtp-draft-tokens 3 --max-concurrency 8 \
  --output /path/to/qwen38-tp4-c8-mtp3.safetensors --verbose

./flare/target/release/flare run /path/to/qwen38-tp4-c8-mtp3.safetensors \
  --publisher-keys /path/to/development-publisher.json \
  --dangerously-approve-key <sha256-of-publisher-key> \
  --dangerously-accept-publisher local-development \
  --gpus 0,1,2,3 --host 127.0.0.1 --port 8102 \
  --embedding-table-storage ram
```

The checkpoint argument accepts a local directory (the recipe's pinned
hashes validate it), which avoids a second hub download. `flare run` takes
no `--config`; the development publisher profile written by the export sits
next to the output package, and the approval flags above are the unattended
first-use path.

Measured on 4× RTX 5090 (preparation 23.7 GiB reserved per GPU):

| | |
|---|---|
| export wall time (warm kernel cache) | ~10 min (tuning 35 s, forward compile 156 s, export write 259 s) |
| weights resident per GPU | 23.50 GiB |
| KV cache | 29.2 GiB total = **1,007,616 tokens** @ concurrency 8 |
| serving resident per GPU | 32,048 MiB |
| max context | 262,144 tokens/request |

## Runtime fix in this fork

`Prepare execution` failed with `cuGraphAddKernelNode_v2 failed (1,
CUDA_ERROR_INVALID_VALUE)` on kernels whose graph nodes record more dynamic
shared memory than the package's per-function attribute snapshot (the
snapshot predates b12x tuning raising the limit; snapshots also differed
across ranks for the same function id). Helios now reports the graph, node,
and kernel on failure, and on this failure raises the function's
`MAX_DYNAMIC_SHARED_SIZE` to the node's recorded requirement and retries
once — the node is the ground truth for what the kernel needs. The fuller
fix belongs on the Ignition recording side; this keeps already-exported
packages servable.
